# 03 — The Watcher

The watcher's only job is to turn filesystem noise into a small number of high-quality
queue rows. It never parses, never hashes, never blocks. If it's doing work, it's wrong.

## Platform backends

| Platform | API | Notes |
|---|---|---|
| macOS | FSEvents | Recursive per-directory-tree, cheap, coalesced by the OS. Best case. |
| Linux | inotify | **One watch per directory.** Hits limits on big repos — see below. |
| Windows | ReadDirectoryChangesW | Recursive, but buffer overflow drops events silently. |

### Backend choice: `fs.watch`, not `@parcel/watcher`

The obvious move is a maintained wrapper (`@parcel/watcher`, chokidar with native backends).
The [native-addon spike](../spikes/native-addon-compile.ts) rules it out: `@parcel/watcher` is a native N-API addon,
and **`bun build --compile` does not embed `.node` files.** The compiled binary fails at
runtime with `Cannot require module ./build/Release/watcher.node` the moment it runs outside
the source tree. That directly contradicts the single-binary distribution pitch.

Bun's built-in `fs.watch` with `recursive: true` is part of the runtime, so it compiles in for
free. The [fs.watch spike](../spikes/fs-watch-recursive.ts) verifies it both from source and inside a compiled
binary on macOS/arm64: one watch covers the whole tree, rename-over-target is observed, and
directories created *after* the watch starts are still covered.

**Event types from `fs.watch` are unreliable** — every change arrives as `rename`, including
plain modifies. This costs us nothing, because the queue treats an event only as "this path is
dirty" and the hash check in [02-queue](02-queue.md) decides what actually happened. Never
branch on the event type.

Still open: **`recursive: true` on Linux.** It must be verified in CI on an actual Linux
runner before Phase 1 closes. If it is unsupported there, the fallback is a watch per directory
(what `@parcel/watcher` does internally anyway), which reintroduces the inotify limits below.

### Linux inotify limits — a real failure, not a theoretical one

Default `fs.inotify.max_user_watches` is often 8192. One watch per *directory* means a
monorepo blows through it, and the failure mode is `ENOSPC` — which looks like a disk error
and, if unhandled, means the watcher silently stops seeing changes.

Handling:

1. Catch `ENOSPC` explicitly.
2. Fall back to **scan mode**: periodic (30 s) `git status --porcelain` + mtime sweep of
   tracked files. Much less responsive, but correct.
3. Warn **once**, with the actual fix:
   `sudo sysctl fs.inotify.max_user_watches=524288`
4. Report degraded mode in `crux.status()` so the user and the agent both know.

Never silently stop watching. A watcher that has quietly died is exactly the stale-index
scenario the whole design exists to prevent.

### Windows buffer overflow

`ReadDirectoryChangesW` drops events when its buffer overflows during a burst. Detect the
overflow signal and respond with a full rescan of the affected subtree rather than assuming
you saw everything.

## Filter before enqueue

Ignore rules are applied **in the watcher**, before anything touches SQLite. Filtering after
enqueue means `npm install` writes 100,000 rows and then deletes them.

Layers, cheapest first:

1. **Hard-coded denylist** — `.git/objects`, `node_modules`, `target`, `dist`, `build`,
   `.next`, `vendor`, `__pycache__`, `*.lock`, `*.min.js`, `*.map`.
2. **`.gitignore`** — full semantics including negations and nested files. Reuse a proper
   implementation; hand-rolled gitignore matching is always subtly wrong.
3. **`.cruxignore`** — same syntax, `crux`-specific, so users can exclude things they still
   want in git (fixtures, large generated schemas).
4. **Heuristics** — file > 1 MB, binary sniff (NUL in first 8 KB), minified detection
   (mean line length > 500), generated-file banners (`@generated`, `Code generated by`).

Everything filtered is recorded once in `files` with `parse_state='skipped'` and a reason,
so `crux.status()` can explain *why* a file isn't searchable. "It's not in the index and I
don't know why" is a bad support experience.

## Debounce and coalesce

Editors don't write files the way you'd expect. A single ⌘S in VS Code typically produces:

```
create   .goutputstream-XYZ   (or  file.ts.tmp)
write    .goutputstream-XYZ
rename   .goutputstream-XYZ → file.ts
```

So you observe a **rename**, not a write, and often 2–3 events for one logical save.

- **200 ms debounce per path**, trailing edge. Long enough to collapse a save burst, short
  enough to feel instant.
- Temp-file patterns (`.tmp`, `~`, `.swp`, `.goutputstream-*`, `#*#`, `4913`) are dropped
  entirely; only the final renamed path is enqueued.
- The queue's unique index handles the rest — even if the watcher over-emits, the coalescing
  upsert collapses it.

## Git-aware shortcuts

Watch `.git/HEAD` and `.git/index` explicitly. They're tiny, and they tell you when
something big is about to happen.

**Branch switch / rebase / merge.** `HEAD` changes. Instead of processing the 5,000
individual file events that are about to arrive:

```
old = previous HEAD sha,  new = current HEAD sha
git diff --name-status <old> <new>
  → enqueue exactly that set at bulk priority (10)
  → suppress the incoming per-file event burst for a short window
```

Cheaper, ordered, and it gives you deletes and renames explicitly rather than inferring them
from event soup.

**Stash / checkout of individual files.** `.git/index` changes without `HEAD` moving →
`git status --porcelain` and enqueue the differences.

Combined with hash-skip and content-addressed chunks, a branch switch to a branch you've
visited before costs a few thousand stats and essentially no CPU.

## Deletes and renames

- Delete → `kind='delete'` job → remove `files` row, `file_chunks` rows, symbols, FTS rows,
  and graph edges originating from that file. Chunks themselves are left for GC, since
  another file may share the hash.
- Rename → delete job for the old path + parse job for the new one. With content-addressed
  storage the parse is nearly free: same chunk hashes, so no re-embedding, just new
  `file_chunks` mappings.

## Cold start

First run on a workspace, before any watching:

1. Walk the tree with ignore rules applied (parallel, `readdir` + `stat`).
2. Bulk-insert `parse` jobs at priority 20.
3. Start the watcher immediately — don't wait for the walk to finish, or edits during the
   initial index get missed.
4. Report progress through `crux.status()`; queries work against the partial index throughout.

**Resumability**: if the process dies mid-walk, the queue rows already written survive.
On restart, a Merkle-style directory hash comparison (store a hash per directory of its
entries' names+mtimes) identifies subtrees that are entirely unchanged and skips walking
them — so restarting a 200k-file index doesn't redo the walk.

## Idle behavior

- No MCP client connected for 2 hours → leader releases its lease and exits. Zero
  background cost when you're not coding.
- Next `crux mcp` connection re-elects a leader, which does a Merkle diff to catch everything
  that changed while nothing was watching, then resumes live watching.
